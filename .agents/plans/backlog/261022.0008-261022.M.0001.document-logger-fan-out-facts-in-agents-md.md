# Document logger fan-out facts in AGENTS.md

- raised: 2026-10-22 — during plan 261022.0008 (harden logger core fan-out), handed to plan 261022.0011 (project hygiene) for review item 4
- decision: open

The fan-out section of `AGENTS.md` ("The fan-out model (`logger.go`)") predates plan
261022.0008 and no longer describes the logger core. The docs plan should add these facts:

- `WriteLog` takes a snapshot of the matching sinks under `l.m.RLock()` and releases the
  lock before writing to any sink. A sink may therefore call `Hook`, `Unhook`, or
  `SetMinLevel`; an in-flight `WriteLog` may still reach a hook removed, or use a level
  changed, after `Unhook`/`SetMinLevel` returned. Only calls starting after they return
  observe the change.
- `WriteLog` returns only after every matching sink returns; a slow sink delays the caller
  and serializes callers sharing that sink.
- A sink panic is recovered on both the inline and the fan-out path and returned as an
  error naming the sink type, wrapping the panic value, and carrying the stack trace; a
  one-line notice also goes to stderr. Callers going through std `log` see it only on
  stderr.
- One mutex per sink identity per logger: every registration of the same pointer sink
  (directly, via `WithMinLevel`, or as a hook) shares one mutex from a never-pruned
  per-logger registry. The logger retains every distinct pointer sink registered during
  its lifetime, including after `Unhook`. Not covered: package factory wrappers
  (`TimestampedHandler(buf)` next to `buf`), value-type sinks, user wrapper types, and
  sharing across loggers.
- `Logger.Write` and `WriterAs(level).Write` return `len(p), nil` for a message filtered
  below the threshold (`io.Writer` contract); `WriteLog` still returns `(0, nil)` when no
  sink matched and `0` when only hooks below the minimum fired.
- The re-entrancy contract: allowed — `Hook`/`Unhook`/`SetMinLevel` and logging to other
  sinks from inside a sink. Deadlocks — logging back into the same sink or another
  registration of it; writing to std `log` from a sink when the outer call came through
  std `log`; writing to the same `WriterAs` adapter the outer call came through; sinks
  that log into each other (A→B and B→A) under concurrent writes.
- `CloseOrPanic(nil)` and `CloseOrLog(nil)` are no-ops; `CloseOrLog` must not be called
  from inside a sink when std `log` is routed through the logger.

# Task Breakdown

## Overview

The project review of 2026-10-22 (main @ 434ed68) found eight defects in the logger core
(`logger.go`, the `writer`/`ensureThreadSafe` guard at the bottom of `handler.go` and
`logger.go`, and `closers.go`):

| Review item | Defect |
|---|---|
| 1 (part) | `WriteLog` holds `l.m.RLock()` while sinks write; a pending `Hook`/`Unhook`/`SetMinLevel` then blocks every new `WriteLog` on the logger until the slowest sink returns. |
| C4 | A hook or handler that calls `Unhook`/`Hook`/`SetMinLevel` from inside its `Write` deadlocks (write lock requested while the same goroutine holds the read lock). |
| 6 | A panicking sink crashes the process when 2+ sinks match (panic in a goroutine without `recover`); with one sink the panic propagates to the caller. |
| 7 | The same non-thread-safe sink registered twice (`NewLogger(l, buf, buf)`, `Hook(buf)` plus handler `buf`, `WithMinLevel(x, buf)` plus `buf`) gets two mutexes, so its `Write` runs concurrently. |
| C7 | `Logger.Write` and `WriterAs(level).Write` return `(0, nil)` for non-empty input filtered below the threshold, violating the `io.Writer` contract (`bufio.Writer.Flush` returns `io.ErrShortWrite`). |
| 20 | Re-entrant logging deadlocks: a sink that calls `CloseOrLog` (std `log`) inside `Write` (`TelegramHandler`, `handler.go:78`) re-enters the logger when std `log` output is routed through `WriterAs`/`StdLog`. |
| 22 | `CloseOrPanic(nil)` and `CloseOrLog(nil)` panic with a nil-pointer dereference, unlike `CloseOrLogError`/`CloseOrJoin`, which treat a nil closer as a no-op. |
| 23 | `WriteLog` carries a dead condition (`!anyHandlerActive && len(sinks) == 0`, where the first operand is implied by the second) and a stale comment claiming the empty-slice case reaches the fan-out branch. |

This plan fixes them without breaking the public API. Out of scope: making
`TelegramHandler` asynchronous (deferred by the owner; it remains a synchronous 20 s POST
behind its own mutex, so a caller whose message matches it still waits), file handlers,
`httptap`, and documentation (`AGENTS.md`/`README.md`, review item 4). Facts this plan makes
documentation-worthy are listed in Task 6 for the docs plan.

## Decisions

Each decision records the reason and the reversal path. Semantic changes are marked
**[semantic]** and each gets a CHANGELOG `Changed` line.

1. **Snapshot under `RLock`, release before any sink write. [semantic]** `WriteLog`
   collects the matching sinks (hooks by exact level, handlers by threshold, including
   `LeveledHandler.MinLevel()`) into a local slice under `l.m.RLock()`, releases the lock,
   then writes. This fixes C4 (a sink may call `Hook`/`Unhook`/`SetMinLevel`) and the
   lock-convoy half of item 1 (a pending `Hook`/`Unhook`/`SetMinLevel` no longer blocks
   unrelated `WriteLog` calls behind a slow sink). New visible semantics: a `WriteLog` that
   took its snapshot before `Unhook(id)` returned may still write to that hook after
   `Unhook` returns; likewise for `SetMinLevel`. `Unhook`/`SetMinLevel` guarantee only that
   `WriteLog` calls *starting* after they return observe the change. No in-tree code or
   test depends on the stronger guarantee, and the stronger guarantee is exactly what
   deadlocks. Reversal: move `RUnlock` back after the dispatch (re-introduces C4).
2. **Keep goroutine-per-sink fan-out for 2+ sinks; keep the inline path for exactly one.**
   Sequential writing would cut the multi-sink cost (baseline: 4 sinks 1397 ns/9 allocs,
   2 hooks 870 ns/7 allocs) to roughly the sum of
   the sinks' own costs, but its latency is the *sum* of sink latencies, not the maximum.
   With `TelegramHandler` still synchronous (20 s timeout), a common setup — a file
   handler plus a Telegram hook on a high level — would delay the file line by up to 20 s
   behind the POST, and lose it if the process dies meanwhile. Real sinks (file:
   open/write/write/close per message, review item 9; stdout syscall) cost microseconds, so
   ~0.3 µs of fan-out overhead per sink is not the dominant cost. The documented fan-out model in
   `AGENTS.md` stays true. Reversal: once no in-tree sink blocks on the network (Telegram
   async lands), a follow-up may switch to sequential dispatch, gated by a benchmark
   showing the win on realistic sinks; record it as a backlog entry then.
3. **`recover()` per sink on both paths, turning a panic into an error. [semantic]** One
   helper `writeSink(w io.Writer, p []byte) (err error)` with a deferred `recover` is used
   by the inline path and by each fan-out goroutine. Recovering only in goroutines would
   make behaviour depend on how many sinks happen to match a given level (the same sink
   would panic the caller at one level and return an error at another). A logger must not
   be the thing that kills or unwinds the caller because one sink misbehaves. The error is
   `fmt.Errorf("loginjector: sink %s panicked: %w", typ, e)` when the recovered value is an
   `error`, `%v` otherwise; `typ` is the `%T` of the unwrapped sink (`writer.original` when
   set, peeled through `*leveledWriter`), not of the guard. Package handlers built by a
   factory (`TimestampedHandler`, `RotatingFileHandler`, ...) carry no `original`, so their
   panics report `*loginjector.writer`; accepted (the message text still identifies the
   failure) rather than adding a name field to every factory. The single-sink path changes
   from "panic propagates" to "error returned" (`Printf`/`Print` print it via `println`, as
   for any sink error). `Panicf`/`Panic` are unaffected: they panic after `WriteLog`
   returns. `runtime.Goexit` (e.g. `t.FailNow` in a test sink) is not a panic and is not
   intercepted. No exported sentinel is added (minimal API); `errors.As`/`errors.Is` reach
   an `error` panic value through `%w`. Reversal: re-panic in `writeSink` on the inline path
   (`panic(r)` after recording), or remove the `recover`.
4. **Deduplicate guards by sink identity within one logger, through a never-pruned
   per-logger lock registry. [semantic]** The identity of a sink is computed by peeling
   `*leveledWriter` layers to the innermost writer; when that writer is a pointer
   (`reflect.TypeOf(w).Kind() == reflect.Pointer`) and is not itself a package `*writer`
   (already self-serialised), every registration of it on this logger uses one mutex taken
   from `Logger.sinkLocks map[io.Writer]*sync.Mutex` (keyed by the peeled pointer, guarded
   by `l.m`, created lazily so a zero-value `Logger` works). Entries are **never removed**,
   including on `Unhook`: an in-flight `WriteLog` may still hold a snapshot of an unhooked
   guard (Decision 1), and a re-registration of the same sink must get the *same* mutex or
   the old in-flight write and the new one race (plan review B, item 7). A scan of the
   current handler/hook slices, considered first, loses exactly that case. Cost: the map is
   bounded by the number of distinct pointer sinks ever registered on the logger, and it
   keeps those sinks reachable for the logger's lifetime; godoc on `Hook` says so (a program
   that hooks a fresh buffer per request grows the map — such a program should use one
   long-lived sink). Pointer-only keys are always comparable, so map hashing cannot panic.
   Coverage, stated precisely: a pointer sink registered more than once directly, via
   `WithMinLevel`, or as a hook. **Not covered:** (a) a sink also passed through a package
   factory that wraps it in a closure (`TimestampedHandler(buf)`, `WithOutput`-style
   options) — the factory returns a `*writer` without `original`, so `buf` registered
   directly as well still gets two mutexes; (b) value-type sinks that hold a pointer to
   shared state; (c) user-defined wrapper types (opaque); (d) one sink shared across two
   loggers (a process-global registry would leak forever without `weak`, Go 1.24, above
   the floor). `NewLogger`/`Hook` godoc lists these gaps. **New deadlock introduced:**
   because duplicate registrations now serialise on one mutex, a sink registered twice (e.g.
   handler `S` and `Hook(S, X)`) whose `Write` logs at a level that reaches its other
   registration now deadlocks, where before it raced; this joins the re-entrancy contract
   (Decision 6) and gets a CHANGELOG `Changed` line. Reversal: drop the registry; every
   registration gets its own mutex again (re-introduces item 7).
5. **`Logger.Write` and `WriterAs(level).Write` return `len(p), nil` when the message is
   filtered. [semantic]** They are `io.Writer`s; a filtered write is a successful,
   intentional discard (the `io.Discard` model), and `n < len(p)` with a nil error is a
   contract violation that `bufio`, `io.Copy`, and `fmt.Fprint` callers treat as a short
   write. On error they return `WriteLog`'s `n` with the error (always `<= len(p)`, so the
   contract holds). `WriteLog` itself is not an `io.Writer` and keeps its documented
   `(0, nil)` for "no sink matched" and `0` for "only hooks below the minimum fired"
   (existing tests `TestLogger_WriteLog`, `TestLogger_HookBelowMinimum` keep asserting it;
   the Axiom plan also relies on it). Reversal: return `WriteLog`'s `n` unchanged from the
   adapters.
6. **Re-entrancy contract, documented and enforced in-tree, not detected at runtime.** After
   Decision 1 a sink may call `Hook`/`Unhook`/`SetMinLevel` and may log through the same
   logger to *other* sinks. These re-entries remain deadlocks and are documented on the
   `Logger` type and on `CloseOrLog`: (a) logging, directly or indirectly, back into the
   same sink (its per-sink mutex is not re-entrant), which after Decision 4 includes any
   other registration of that sink on the same logger (handler plus hook, or two
   `WithMinLevel` views); (b) writing to std `log` from a sink when the outer call itself
   came through std `log` (`log.Logger` holds its own output mutex); (c) writing from a sink
   to the same `WriterAs` adapter the outer call came through — that adapter's mutex is held
   for the whole fan-out, including a 20 s Telegram POST. Go has no goroutine identity to detect this cheaply, and a `TryLock`
   scheme would turn deadlocks into silently dropped lines. In-tree, `TelegramHandler`
   stops calling `CloseOrLog` inside `Write` (`handler.go:78`); this is the only
   production call site (`grep -rn 'CloseOrLog(\|log\.Print' --include='*.go'`). Reversal:
   none needed; the godoc is additive.
7. **`CloseOrPanic(nil)` and `CloseOrLog(nil)` become no-ops. [semantic]** Matches
   `CloseOrLogError`/`CloseOrJoin`, which already document "a nil c is a no-op"; the
   current behaviour is an accidental nil-pointer panic, not a designed signal. Only an
   untyped nil interface is a no-op; a typed nil (e.g. `(*os.File)(nil)`) still calls
   `Close`, exactly like the sibling helpers. Reversal: remove the guard.
8. **Keep the `WriterAs` adapter as a `*writer` (with its mutex).** The mutex is held for the
   whole `WriteLog` fan-out, so all writers through one adapter wait for its slowest
   matching sink (up to a 20 s Telegram POST), and re-entering the same adapter from a sink
   deadlocks on it (Decision 6 (c)). Removing it now buys little: `StdLog` callers are
   already serialised for the same duration by `log.Logger`'s own output mutex, and the
   Axiom plan's Task 1 relies on "a `*writer` built by `WriterAs` has `original == nil`".
   Only its return value changes (Decision 5). Reversal: a follow-up may replace it with a
   lock-free adapter (benefits direct `WriterAs` users, not `StdLog`); record as backlog.

### Interaction with plan 261021.0006 (Axiom)

- Axiom Task 1 introduces `writeSink(w io.Writer, level LogLevel, p []byte)`. This plan
  introduces `writeSink(w io.Writer, p []byte) (err error)` with the `recover`. Axiom then
  adds the `level` parameter and the `LevelWriter` preference *inside* the same helper; the
  `recover` covers `WriteLevel` too. No second dispatch point.
- Axiom's `*writer.WriteLevel` must take the same lock as `Write`, which after Task 3 is
  `w.lock()` (the shared mutex when set), not `w.m` directly. Add this note to plan
  261021.0006 Task 1 "Pitfalls" when this plan is implemented (one-line edit of that plan,
  part of Task 6 here).
- Axiom's `leveledWriter.WriteLevel` does not affect identity peeling (Task 3 peels by
  type, not by method set).
- Axiom asserts "Return values of `WriteLog` are unchanged"; Decision 5 keeps them.
- Axiom's async handler returns quickly from `Write`, so it benefits from Decision 1 (its
  `Shutdown`/`Unhook` paths no longer convoy behind other sinks) and needs nothing else.

## Tasks

Gate for every task and for the branch:
`test -z "$(gofmt -l .)" && go vet ./... && CGO_ENABLED=1 go test -race ./... && make lint`

Test conventions: canonical subtest form under one `Test<Type>_<Method>` per method; new
concurrency tests are named `…ForRaceCondition`; tests that would hang on current code run
the call in a goroutine and fail with `t.Fatal` after a 2 s `time.After`, unblocking any
parked sink in `t.Cleanup` so the test binary does not hang, and every goroutine a test
starts is joined (`sync.WaitGroup` or a done channel) before the test returns. "Wait until
a writer is pending on `l.m`" is detected by polling, never by sleeping:
`for l.m.TryRLock() { l.m.RUnlock(); select { case <-setDone: goto done; default:
runtime.Gosched() } }; done:` (`TryRLock` fails once a writer waits; Go 1.18+). The poll
must have that second exit (`setDone` closed by the writer goroutine when its call
returns): on fixed code the lock is free, the writer finishes at once, and a single-exit
poll spins forever; on current code the pending state persists, so the deadlock still
reproduces. Re-entrancy tests use this fixed routing so a sink never
receives its own re-entrant message after the fix: `minimum = M`; sink A =
`WithMinLevel(H, a)` with `H > M`, fired by `WriteLog(H)`; sink B = `Hook(b, L)` with
`L < M`, fired only by `WriteLog(L)` (hooks ignore the minimum, A's threshold excludes
`L`); any concurrent `SetMinLevel` sets a value `M' < H` with `M' > L`, so neither A's nor
B's routing changes. Use
`internal/synctest.SafeBuffer` where a test only needs a thread-safe sink, and a plain
`*bytes.Buffer` where the test proves the logger serialises a non-thread-safe sink.

### Task 1: Snapshot sinks under the read lock and release it before writing

- Description: Rewrite `Logger.WriteLog` (`logger.go:147`) into two phases.
  Phase 1 (under `l.m.RLock()`, released explicitly, not by `defer`): build
  `sinks := make([]io.Writer, 0, len(l.hooks)+len(l.handlers))` with hooks where
  `level == h.Level`, then handlers where `level >= threshold` (`unwrapLeveled` /
  `MinLevel()` as today), tracking `handlerMatched bool`. Phase 2 (no lock): if
  `len(sinks) == 0` return `(0, nil)`; one sink → inline; 2+ → fan-out. Return value rule
  unchanged: `n = len(message)` when `handlerMatched`, else `0`. Remove the dead
  `!anyHandlerActive &&` operand and the stale "empty sink slice ... lands here" comment
  (item 23). Update the `WriteLog` godoc: the lock is held only while matching sinks;
  sinks may call `Hook`/`Unhook`/`SetMinLevel`; an in-flight call may still reach a hook
  removed or a level changed after its snapshot (Decision 1). Update `Unhook` and
  `SetMinLevel` godoc with the "calls starting after return" guarantee.
- Acceptance Criteria:
  - New subtests, each failing on current code by timing out (deadlock). Routing follows
    the fixed re-entrancy setup in "Test conventions" (A = `WithMinLevel(H, a)`, B =
    `Hook(b, L)`, minimum `M`, `L < M < H`; any concurrent `SetMinLevel` uses `M'` with
    `L < M' < H`):
    - `TestLogger_Unhook/hook calling Unhook from its Write does not deadlock`: a hook whose
      `Write` calls `l.Unhook(id)` (id captured before the first write); `WriteLog` at the
      hook's level returns within 2 s; a second `WriteLog` at that level no longer reaches
      the hook.
    - `TestLogger_Hook/handler registering a hook from its Write does not deadlock`: handler
      A's `Write` calls `l.Hook(c, L)` inside a `sync.Once` (so repeated writes do not
      register repeatedly), targeting a different sink `c`; `WriteLog(H)` returns within
      2 s; a following `WriteLog(L)` reaches `c`.
    - `TestLogger_SetMinLevel/does not wait for a blocked sink`: A's `Write` signals
      "entered" and parks on a channel; the test calls `WriteLog(H)` in a goroutine, waits
      for "entered", then calls `SetMinLevel(M')` (must return within 2 s) and
      `WriteLog(L)` (reaches only B; must return within 2 s and B holds the line). Cleanup
      closes the channel and joins the goroutine. On current code `SetMinLevel` waits for A,
      and `WriteLog(L)` queues behind the pending writer.
    - `TestLogger_WriteLog/sink logging to another sink while SetMinLevel is pending`: A's
      `Write` starts a goroutine calling `SetMinLevel(M')` that closes `setDone` on return,
      polls with the two-exit loop from "Test conventions" until that writer is pending or
      `setDone` is closed (the fixed code takes the second exit), then calls `l.WriteLog(L, ...)` (reaches only B). `WriteLog(H)` from the test
      completes within 2 s, B holds the line, and the `SetMinLevel` goroutine is joined
      before the test returns. On current code the re-entrant `RLock` blocks behind the
      pending `Lock`, which waits for the outer `RLock`.
  - `TestLogger_UnhookForRaceCondition`: 8 goroutines call `WriteLog` while 4 goroutines
    loop `Hook`/`Unhook` on one `synctest.SafeBuffer` hook sink and 2 loop `SetMinLevel`;
    `-race` clean; no panics. (A thread-safe sink here, because duplicate registrations of a
    plain buffer only become safe in Task 3; the plain-`*bytes.Buffer` variant is a Task 3
    criterion.)
  - Existing `TestLogger_WriteLog`, `TestLogger_HookBelowMinimum`, `TestWithMinLevel_Logger`,
    `TestLogger_WriteForRaceCondition` pass unchanged (return-value rules preserved).
  - `BenchmarkWriteLog` "1 sink" sub-benchmarks keep 0 allocs/op.
- Pitfalls & edge cases:
  - Do not keep `defer l.m.RUnlock()`. Keep phase 1 inline in `WriteLog`, with a single
    exit and an explicit `l.m.RUnlock()` after the loops. Do not extract a `snapshot`
    method that returns the slice: escape analysis keeps the `make` at `logger.go:154` on
    the stack today, and returning it moves it to the heap, breaking the 0-allocs
    single-sink criterion. If extraction is wanted, pass a caller-owned buffer
    (`l.snapshot(level, buf[:0])`) and verify with `go build -gcflags=-m` and the benchmark.
  - `MinLevel()` is called under the read lock as today; it must not call back into the
    logger (already documented on `LeveledHandler`).
  - The local `sinks` slice holds copies of interface values; `Hook` appending to
    `l.hooks` after release cannot affect it. Do not alias `l.handlers` directly.
  - A zero-value `Logger{}` (no handlers) must still return `(0, nil)` without panicking.
- Complexity: Medium

### Task 3: Share one mutex per sink identity within a logger

- Description: In `handler.go`, extend `writer` with `shared *sync.Mutex` (nil for every
  factory-built writer) and an unexported `lock() *sync.Mutex` returning `shared` when set,
  else `&w.m`; `(*writer).Write` uses `w.lock()` with a deferred unlock. In `logger.go`:
  - Add `sinkLocks map[io.Writer]*sync.Mutex` to `Logger` (guarded by `l.m`; lazily
    created; never pruned — Decision 4).
  - Add `sinkIdentity(w io.Writer) (key io.Writer, ok bool)`: peel `*leveledWriter`
    layers; if the innermost is a `*writer`, `ok=false` (self-serialised); if
    `reflect.TypeOf(inner).Kind() != reflect.Pointer`, `ok=false`; else `key=inner`.
  - Replace the free function `ensureThreadSafe(w)` with a method
    `(l *Logger) ensureThreadSafe(w io.Writer) io.Writer`, called with `l.m` held (or
    before `l` is published, in `NewLogger`): an input `*writer` is returned unchanged (as
    today); otherwise build `&writer{original: w, h: w.Write}` and, when `sinkIdentity(w)`
    is ok, set `shared` to `l.sinkLocks[key]`, creating the entry on first sight.
  - `NewLogger` builds the `Logger` value first, then registers handlers through it.
    `Hook` already holds `l.m.Lock()`.
  - Godoc on `NewLogger` and `Hook`: what is covered (a pointer sink registered more than
    once directly, via `WithMinLevel`, or as a hook — one mutex for all); what is not
    (package factory wrappers such as `TimestampedHandler(buf)` registered alongside `buf`,
    value-type sinks sharing state through a pointer, user wrapper types, sharing across
    loggers — the caller guards those); that the logger keeps every registered pointer sink
    reachable for its lifetime; and that duplicate registrations serialise, so a sink must
    not log into another registration of itself (Decision 6 (a)).
- Acceptance Criteria (each race test fails under `-race` on current code):
  - `TestNewLoggerForRaceCondition` with subtests `same buffer twice` (`NewLogger(l, buf,

## Risks

- **Weaker `Unhook`/`SetMinLevel` guarantee (Decision 1).** A consumer that closes a hook's
  underlying resource immediately after `Unhook` may see one late write against a closed
  resource. Mitigation: godoc and CHANGELOG state it; no in-tree code does this. If a
  consumer needs a barrier, a follow-up can add a quiescence mechanism (e.g. a per-logger
  in-flight `WaitGroup` awaited by an opt-in `UnhookWait`), which is additive.
- **Single-sink panic no longer propagates (Decision 3).** A consumer relying on a sink
  panic to abort the request path loses that; Printf/Print now print the error to stderr.
  Considered acceptable: no in-tree or known consumer relies on it (fleet of seven pins
  v1.0.3–v1.0.5, project memory); recorded in CHANGELOG `Changed`.
- **Recovered panic leaves the sink's own state inconsistent.** The logger keeps calling
  it; repeated errors follow. Acceptable: that is the sink's defect; the logger stays alive.
- **Dedup gaps (Decision 4).** Not covered: a sink also registered through a package
  factory wrapper (`TimestampedHandler(buf)` next to `buf` — the factory's `*writer` has no
  `original`), value-type sinks sharing state through a pointer, user wrapper types, and
  cross-logger sharing. Documented in `NewLogger`/`Hook` godoc; the race-detector tests pin
  the covered cases. Closing the factory gap would need every factory to record its inner
  writer; a follow-up if a consumer hits it.
- **New deadlock from shared mutexes (Decision 4).** A sink registered twice whose `Write`
  logs into its other registration used to race and now deadlocks. Documented in the
  re-entrancy godoc and CHANGELOG `Changed`; no in-tree sink logs from `Write` after Task 5.
- **Registry retention (Decision 4).** The never-pruned lock map keeps every registered
  pointer sink alive for the logger's lifetime; a program that hooks a fresh sink per
  request grows it without bound. Documented on `Hook`; pruning safely needs the in-flight
  quiescence mechanism mentioned above.
- **Slow sinks still slow the caller.** Decision 1 removes the lock convoy, not the
  `WaitGroup` wait or the per-sink mutex queue behind a slow `TelegramHandler`. That half of
  item 1 is the deferred Telegram-async work.
- **Fragile area:** `WriteLog` is the hot path and the Axiom plan modifies it next. Keep the
  diff confined to the two-phase shape and `writeSink`; benchmarks in Task 6 guard it.

## Trade-offs

- Chose snapshot-then-release over holding the lock for the dispatch, because holding it is
  what deadlocks re-entrant sinks and convoys all callers behind the slowest sink; the cost
  is the weaker "in-flight" guarantee for `Unhook`/`SetMinLevel`.
- Chose to keep goroutine-per-sink fan-out over sequential writes, because with a
  synchronous network sink in-tree, sequential latency is the sum of sinks and delays local
  durable sinks behind the network; the cost is ~0.3 µs and one to two allocations per
  extra sink (baseline: 4 sinks 1397 ns/9 allocs), small next to real sink I/O. Revisit after Telegram async.
- Chose `recover` on both paths over goroutine-only recovery, because behaviour must not
  depend on how many sinks match a level; the cost is that a single-sink panic no longer
  reaches the caller.
- Chose a never-pruned per-logger lock map keyed by the peeled sink pointer over a scan of
  the current registrations (loses the in-flight-after-`Unhook` case, plan review B item 7)
  and over a process-global registry (leaks across loggers without `weak`), because it is
  panic-free and race-free in every covered case; the costs are retention of registered
  sinks for the logger's lifetime, cross-logger sharing staying the caller's
  responsibility, and serialisation that turns self-logging across duplicate registrations
  into a deadlock.
- Chose `len(p), nil` for filtered writes in the `io.Writer` adapters while keeping
  `WriteLog`'s `0`, because the adapters must satisfy `io.Writer` and `WriteLog`'s return
  value is a documented, tested, and depended-on signal ("nothing matched").
- Chose documenting the re-entrancy contract and removing the in-tree violation over runtime
  detection, because Go exposes no cheap goroutine identity and `TryLock`-based detection
  would replace deadlocks with silently dropped log lines.
- Chose nil-closer no-op for `CloseOrPanic`/`CloseOrLog` over keeping the panic, for
  consistency with the sibling helpers that already document it.

- (d) Consensus decision (opus + Codex sol, 2026-10-22): keep the never-pruned sink-lock

  documented instead, on `NewLogger`, `Hook`, and `Unhook`. Reversal: snapshot-aware
  reclamation (an in-flight counter per registry entry, released when the last snapshot
  holding it completes) if transient per-request hooks become a requirement.
